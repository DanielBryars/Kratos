# Last-slot fairness across worker capabilities

The registered-worker scheduler keeps submission-time order (`submitted_at`, then job ID)
among due jobs. A future earliest-start time is an eligibility gate, not a reservation. This
increment preserves that ordering rather than introducing the priority/eligibility-time policy
proposed in the broader queue architecture.

## Behaviour

An optional project concurrency limit counts assigned, running and cancelling jobs. When only
one slot remains, the scheduler considers the oldest due job runnable by the requesting worker
or an eligible idle peer in the same project. If only a peer can run that job, the requesting
worker receives no new assignment on this heartbeat. The peer can take the older job on its own
authenticated heartbeat. Repeated polling by a legacy worker therefore cannot consume that last
slot with newer plain jobs ahead of an older output or dataset job.

Peer eligibility requires an idle worker, a heartbeat within the last 90 seconds (three normal
heartbeat intervals), an unrevoked/unexpired worker credential, valid capability and GPU-health
evidence, at least one GPU, and no active attempt. A peer from another project never participates.
The current single-GPU protocol features are cumulative: outputs require protocol 1.1 and dataset
inputs require 1.3. Both direct assignment and peer selection use the same derived job requirement.

No slot is persistently reserved. With two or more free slots, or with no project limit, the
requesting worker takes its oldest compatible job normally. One idle peer with many older jobs
can therefore protect only the last slot, not every spare slot. Ineligible, future, cancelled or
attempt-exhausted jobs do not protect a slot. Running jobs are never preempted.

## Concurrency and liveness boundaries

Assignments retain the worker → project → job lock order. The project lock serializes slot
counting and admission. Peer workers are read without locks to avoid a cycle between concurrent
heartbeats holding their own worker rows. Jobs use `FOR UPDATE SKIP LOCKED`, so a temporarily
locked older job can be skipped; this is not a strict global FIFO promise.

Peer availability is a snapshot. A peer that disconnects immediately afterward may temporarily
delay newer work, but ceases to qualify after 90 seconds without a new heartbeat. Credential
revocation, busy state and capability changes take effect when visible to the next scheduling
decision. The snapshot never authorizes an assignment to that peer: the normal authenticated
heartbeat remains mandatory. Existing assignments replay before any new-work fairness or quota
decision.

Progress assumes the compatible peer continues making valid scheduling heartbeats, transactions
finish, and running work eventually releases slots. This addresses repeated overtaking of older
jobs under a project cap; it does not establish universal starvation freedom, cross-project
sharing, per-user fairness, or a priority policy. New non-cumulative constraints (GPU models,
memory, locality, trust or group placement) must replace the protocol-ceiling shortcut with exact
worker/job compatibility before participating in this decision.

## Validation

PostgreSQL tests exercise last-slot protection, peer assignment, freshness expiry and invalid
peers, unused capacity, future/exhausted jobs, replay, project isolation and simultaneous
schedulers held behind a project-row lock. The existing concurrency, protocol, lease, output and
dataset tests remain required. CI is the execution evidence; this document does not claim a live
GPU acceptance run.

The console describes the policy beside project concurrency controls. Its generic queue wait
text does not claim to diagnose which peer or scheduling decision is blocking a particular job.
