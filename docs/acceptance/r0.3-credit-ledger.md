# Project credit ledger foundation

This increment records internal whole credit units. It introduces no money conversion, price,
automatic grant, job charge, reservation or execution limit. The balance never gates scheduling.
It is a foundation for CST-001/003/004/005 and USR-010, not completion of R0.3 credit acceptance.

## Delivered interface

Authenticated project operators can read their project's balance and paginated entry history at
`GET /api/v1/operator/credits`. The console labels this as bookkeeping only. An absent account
is reported explicitly with a zero balance; reading it does not create an account or grant.
The view is a snapshot refreshed by the user. Older history pages use sequence cursors.

Balances, amounts and sequences travel as decimal strings, preserving PostgreSQL bigint values
without rounding in JavaScript. Units are indivisible accounting units in this release, with no
implied GPU-time or currency conversion. Future pricing must define and version that mapping.

The backend supports grants, signed adjustments and exact compensating reversals through
`POST /api/v1/operator/credits/entries`. A required UUID `Idempotency-Key` identifies each
request within its project and actor. Repeating an identical canonical request returns its
original entry; changing it under the same key conflicts. A reversal derives its amount from
the original entry and can undo a non-reversal entry only once, in the same project.

## Write authority stays disabled by default

The `project_credit_managers` table starts empty. Ordinary project membership does not grant
credit-management authority. A writer must have both an active manager designation and active
operator membership in the project. There is no manager bootstrap or grant-management API in
this release, and the console exposes no credit-writing controls. No production manager,
account or balance is seeded by the migration.

Enabling manager assignment needs a separate, explicitly defined authority/delegation policy.
Test fixtures create manager rows only in isolated test databases. Deployment must not be
followed by manual grants or role changes as an implicit acceptance step.

## Accounting invariants

Entries are append-only; corrections add entries rather than editing history. The database
rejects entry UPDATE, DELETE and TRUNCATE operations and protects the cached balance from
unexplained changes. This protects normal application access, not against a database owner
deliberately changing the schema or disabling protections.

Amounts are nonzero signed integers; grants are positive. Checked arithmetic prevents overflow,
and committed balances cannot be negative. Account writes serialize, allocate a consecutive
sequence and commit the entry, balance and audit event together. A rollback leaves no consumed
idempotency key or sequence gap. Unused or missing accounts do not affect job admission.

## Required validation

PostgreSQL tests must cover concurrent debits, duplicate writes, rollback/retry, exact reversal,
cross-project isolation, membership/manager revocation, invalid and oversized numbers, mutation
guards, pagination and balance reconciliation. Web tests must preserve numbers beyond
JavaScript's safe integer range and reject malformed balance/cursor responses. CI and deployed
read-only health/API checks supply evidence; no live grant or billable workload is needed.

## Remaining work for Claude

Define manager authority and delegation before enabling writes. Then implement versioned rates
and quotes, separate reserved-balance accounting, atomic holds/releases, durable deduplicated
usage, settlement and platform-absorbed overrun. Worker budget and shutdown enforcement must be
proved end-to-end before describing a reservation as an enforced execution budget. Per-user
attribution and spending limits remain part of that later work.
